⚡ 五条最值钱的通用教训

  1. 第三方网关文档枚举不可信，必须实测真实响应。 成功态 succeeded/completed 写法不一；无效 Key 报错形态需拿假 Key 打一次确认。
  2. 轮询逻辑必须对「查询失败」和「状态读不出」显式处理。 0.2.0 当前尚未做熔断（见 B 层已知短板），长视频轮询遇网关抖动可能静默空转。
  3. HTTP 状态码语义会被重载。 403 同时表示「余额不足 / 无权使用模型 / Key 失效」三种不同问题，顺序写错会把用户引向死路。
  4. 限流（429）与服务器错误（5xx）不宜共用阈值。 429 是暂时的、退避后大概率恢复；5xx 才该快速失败。
  5. 改同一文件禁止并行 Edit，改用原子批量替换脚本。 并发写同文件会静默丢写（返回 success 但磁盘没改）。

A. PT 网关 / API 认知类

文档不可信
共同特征：官方文档与网关真实行为不一致，或状态码语义被重载。只能靠实测取证。
A.01成功态枚举写法不一：succeeded / completed 都可能出现高
现象长视频日志卡在「排队中」，但 PT 后台早已完成，客户端卡着不动。
根因提交页示例写 succeeded，查询页示例写 completed——不同文档页 / 不同模型写法不一，无统一契约。我们这轮实测（wan3.0-video 480p）返回的是 succeeded（queued→in_progress→succeeded），不是 completed（更正旧档案）。
解法多路兜底：① 拿到 metadata.url 即判成功（最强）② status 命中成功词表（succeeded/completed/finished/done/ready）③ progress≥100。poll_task 已实现 ①②。
教训「拿到产物地址」是比「状态等于某个词」强得多的信号。
A.02查询返回非 200 时旧逻辑会空转 —— ⚠️ 0.2.0 已知短板（未做熔断）短板
现象若 GET /v1/videos/{id} 反复 429/5xx，响应无 status → 状态变空 → 既不匹配成功也不匹配失败 → 继续 sleep 轮询，空转到 POLL_TIMEOUT(600s)。
当前poll_task 仅做「超时抛错 + 提示稍后单独 GET 复查」，没有 429 退避 / 5xx 计数熔断 / 未识别状态计数熔断。
路线图加三重熔断：连续 8 次 5xx 失败退出；status 读不出计数 40 次熔断并打印原始响应；429 单独计数 + 指数退避（上限 60s）。
教训「静默继续」是轮询最危险的默认分支。
A.03429 与 5xx 不宜共用严阈值（同 A.02 路线图）中
根因429 是暂时的、退避后大概率恢复；长视频轮询几十次极易撞限流。严阈值会在任务正常生成途中误杀。
解法429 单独计数 + 阈值放宽到 30 + 指数退避；5xx 严阈值快速失败；查询成功两计数器都重置。
A.04403 语义重载：余额不足 / 无权 / Key 失效 三选一（真实，实测遇到）致命
现象余额不足报 403，形如 token quota is not enough ... need quota: ＄0.200000（我们这轮 720p 提交即触发）。
当前0.2.0 未做细分类（classify_rest 未实现），统一 [error] 生成失败：{message} 把网关原文透传——至少不误导方向。建议后续按「先具体特征（token_invalid/quota/not permitted）后状态码兜底」重排。
教训错误分类的价值在把用户引向正确修复路径；当前靠用户 / agent 读原文。
A.05无效 Key 的报错形态 —— ⚠️ 待实测（0.2.0 未验证）待实测
说明我们这轮只用真实 Key，没拿假 Key 打 REST 端点，无法证实「HTTP 500 + token_invalid」。鉴权用 Authorization: Bearer <token>，实测可用。
建议接新网关第一件事——拿假 Key 打一次，记录真实返回再补进分类器。旧档案把此条写成「已确认事实」，此处降为待实测。
A.06GET /v1/models 返回「该令牌被授权的模型」，不是全局目录高
现象同事 Key 不限制模型时正常出片；开了模型白名单后生成报「key 没有权限」。
根因/v1/models 反映该 Key 的可用模型（白名单精确匹配）。显示名「Wan 3.0」与真实 ID wan3.0-video 易不一致。我们实测新 Key 返回 32 个视频模型（口径：仅 video；含全部类型会更多，需注明口径，更正旧档案「85 个」）。
解法提交前 precheck：显式 -m 先与 /v1/models 比对，不在则 1 秒内 exit 3、不进生成不扣费，给相近候选 + 大小写纠正（precheck_explicit_model 已实现）。当前是「不存在则报错退出」，非「跳过该 Key 换下一个」。
A.07「PT 有 900s 硬上限」是误判 —— 异步生成服务端无上限（真实，用户纠正）高
根因908s 是客户端轮询放弃的时刻，非 PT 限制。用户明确纠正：生成异步，无 900s 上限。
解法pt_video.py：提交超时 120s、轮询间隔 10s（均按用户要求）；整体轮询总上限 600s（仅防无限轮询，非 PT 限制；真实出片约 3 分钟，120s 总上限会失败，故默认 600s，可 --timeout 调）。
教训看到超时数字先分清「谁超时了」。
A.08「无可用渠道」多为瞬时故障，不是用户 Key 问题中
根因① 令牌层（Key 绑白名单）→「无权使用模型」；② 渠道路由层（网关找「支持模型+有余额+未禁用」上游）→「无可用渠道」。绝大多数是 ② 瞬时故障。
解法先 models 确认模型在列表，再用完全相同命令复现；话术明确「不是你的 Key 问题」。
A.09无余额查询接口，消耗只能估算（真实，estimate 已实现）中
根因/v1/dashboard/billing/* 全 404，无可编程查余额接口；提交即预扣。
解法用真实探测的预扣单价表估算并标「估算」。余额不足提交必 403 但不扣费，403 返回该模型 required pre-consume 真实额。系数：时长线性、1080p=720p×2。未知模型打印「未知」，绝不瞎编（estimate_cost 已实现）。
A.10media 只收 http(s) URL；@xxx 占位符不识别低
现象① 想传本地截图生成视频；② prompt 写 @male_lead 锁角色，出来却是通用形象。
解法本地路径直接报错（前置防护）；锁角色走 --ref-image / --first-frame 等 media 类型。reference_* 与 first_frame/last_frame 互斥。
A.11【新增 · 致命】请求体枚举字段必须传字符串（我们这轮真踩，旧档案遗漏）致命
现象第一次提交直接报错：json: cannot unmarshal number into Go struct field .seconds of type string。
根因seconds 是 enum<string>；size(480P/720P/1080P)、ratio(adaptive/16:9)、model 同为字符串枚举。传整数 / 小写会被拒。
解法pt_video.py 提交时 "seconds": str(args.duration)、"size": args.resolution.upper()，ratio/model 均字符串，再 json.dumps。所有枚举字段统一转 str。
教训REST 提交前先确认每个字段类型——枚举字段宁可显式转字符串，是最易踩、最可复现的坑。

D. git 沙箱类

跨项目通用
git loose ref 写入不落盘是一切怪象总根源。核心：绕开一切会动 ref 的 git 命令。
#坑解法
D.24push 凭据失败（terminal prompts disabled）命令行临时改用 gh 凭据助手，不写持久配置。
D.25loose ref 写入不落盘（rev-parse unknown）write-tree + commit-tree -p，再 fs.writeFileSync 手写 ref（先建父目录）。
D.26reset --hard 破坏更隐蔽用 Node 重写 ref+HEAD，再 read-tree 修 index，别用 reset --hard。
D.27远程跟踪 ref origin/* 也会丢用本地分支 ref 或 commit SHA 合并（merge --no-ff <sha>）。
D.28checkout/merge 漏写工作树git checkout -f -- . 从 index 重建（不写 ref）。
D.29拿陈旧本地 ref 做历史判定→假结论❌ 禁 git log origin/xxx|grep；✅ 不可变 SHA + merge-base --is-ancestor（tip 来自 ls-remote）。
D.30ls-tree 不加 -r 回显为空加 -r；组合 ls-tree -r + diff --name-only + cat-file -t。
D.31与其他 agent 共用工作目录零接触提交（临时 index + commit-tree + SHA refspec 推送）。
D.32比字节数校验→误判先归一化行尾（CRLF→LF）再比。
